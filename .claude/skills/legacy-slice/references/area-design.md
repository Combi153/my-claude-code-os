# 영역 설계 — 페이지들이 나눠 쓰는 문서

슬라이스마다 다시 만들지 않는 것을 여기 둔다. v2 는 설계서를 페이지 묶음마다 새로 썼고(한 번에 77 KB), 그 안의 대부분은 같은 영역의 다음 묶음에서 거의 바뀌지 않는 결정이었다. **작업 단위를 페이지 하나로 줄이는 것이 성립하려면 이 문서가 있어야 한다** — 없으면 페이지마다 같은 결정을 다시 내리고, 그것이 "작게 자르면 고정 비용을 두 번 낸다"는 반론을 사실로 만든다.

자리: `<docs.root>/<docs.designDir>/<영역>.md`. **제자리에서 개정한다.** 같은 영역을 설명하는 문서가 둘이 되는 순간 어느 쪽이 정본인지 아무도 모른다.

## 이 문서가 지는 것 (영역당 한 번)

| 절 | 무엇 | 언제 바뀌는가 |
|---|---|---|
| 자원과 API 모양 | 영역이 노출하는 자원, 그것이 **화면 모양이 아닌 이유**, 호출자 전부의 계약 | 새 호출자가 기존 계약으로 표현되지 않을 때 |
| 계층 배치 규약 | `도메인`·`화면`·`경계` 분류가 이 영역에서 각각 어느 모듈·계층으로 가는가 | 아키텍처 규칙이 바뀔 때 (실제로 한 번 뒤집혔다) |
| 에러 매핑 | 레거시의 실패 모양(200 + 리다이렉트 본문 포함)이 새 API 의 무엇으로 가는가 | 새 실패 모양을 만날 때 |
| 인가 | 이 영역의 페이지들이 요구하는 권한과 그것을 어디서 판정하는가 | 새 권한 축이 생길 때 |
| 반환 형태 규약 | 어댑터가 레거시 배열로 되돌릴 때의 키·순서·널 규칙 | 템플릿이 새 형태를 요구할 때 |
| 결정 이력 | 되받아친 결정과 그 이유. 페이지별 델타에서 올라온 것 | 매 페이지 |

## 페이지별 델타가 지는 것

`02-design-delta.md` 는 **이 페이지의 규칙들만** 다룬다: 규칙 배치(원장 행 → 모듈·계층·심볼) · 부재 점검 · 교정표 · 표류 의심(각각 원장 행 ID) · 되받아칠 결정.

**델타가 영역 문서와 어긋나면 영역 문서를 고치고 그 사실을 델타에 적는다.** 어긋난 채로 두면 다음 페이지가 옛 규약을 따르고, 두 페이지가 서로 다른 계약으로 같은 API 를 부른다.

## 첫 페이지와 두 번째 페이지

첫 페이지에서 이 문서는 거의 비어 있고, 설계자가 위 여섯 절을 처음 채운다. 그 회차의 설계 비용이 가장 크다. **두 번째 페이지에서 델타가 실제로 얼마나 작아지는지가 이 구조의 유일한 검증이다** — 그 숫자를 `state.json` 에 기록하고, 줄지 않으면 영역 문서가 페이지별로 갈라지는 결정을 담고 있다는 뜻이므로 무엇이 그것인지 찾는다.
